# Dashboard, network restrictions and storage monitoring — work in progress

User decisions: administrators set role priority for default dashboard layouts; a designated emergency account is exempt from network restrictions; storage warnings are in-app only. No configuration or security enforcement has been enabled by this work.

Security invariants: widget visibility never grants data permissions; network enforcement applies only to defined administration functions and only when enabled; client IP is trusted only when the immediate proxy is explicitly trusted; emergency bypass is bound to a designated active account and audited; network configuration must not silently lock all administrators out. Storage totals and historical trends must be derived from actual measured data and reported as unavailable when measurement fails.

Current evidence: standalone IPv4/IPv6 CIDR and trusted-proxy chain parsers have unit tests. They are not connected to request handling, a configuration API, or any UI. The existing user-preference API accepts a bounded dashboard layout using known widget IDs, visibility and width. Personal layouts are connected to the existing dashboard through the shared drawer and reorder components, while only widgets supplied by the authorized dashboard are rendered. A new role layout table and configuration endpoint provide access-profile defaults with numeric priority and an audit entry. Unit and component tests cover permission refusal, input validation and the dashboard views. Role priority and configuration were not verified against a deployed database; drag and mobile behavior were not verified in a browser.

Network enforcement, emergency account administration, telemetry collection and alerts remain to be implemented and validated. A pure network-policy decision and a measured-object accumulator have focused unit tests; the policy is not connected to live requests. A read-only MinIO measurement method now enumerates versions in the configured records and templates buckets, excludes delete markers, and classifies objects using the registered storage domains. It does not return a partial scan after a listing failure. The method is not connected to an API, scheduler, history, alerts, or UI, and it does not account for files stored outside those MinIO buckets. MinIO measurement has not been integration-tested against a real server; its byte count is object-version size, not physical disk consumption. No policy currently uses the proxy or CIDR parsers. This record does not assert GMP compliance.

2026-10-27 evidence: backend compilation and the focused `StorageUsageAccumulatorTest`, `NetworkCidrTest`, `NetworkClientAddressTest`, and `AdministrativeNetworkPolicyTest` passed. The accumulator test checks all registered storage domains and an unrecognized prefix. No migration, request enforcement, or deployment has been performed for these two features.

## Additional work in progress

A scheduled, single-worker MinIO sampler saves only complete scans in `storage_usage_snapshot`; failed scans are not stored as zeroes. An administrator-only API exposes the last 90 days and permits setting an object-version byte budget and warning percentage. The threshold comparison is performed on the server with overflow-safe arithmetic; policy changes write before/after audit values in the same transaction. The Integrations view shows the latest successful timestamp, breakdown, trend and a warning based on that last successful measurement. The budget is an administrator-supplied target, not physical capacity.

The V691 migration and scheduled scan have not been applied or integration-tested against PostgreSQL and MinIO. The sampler now holds a PostgreSQL session advisory lock across scan and persistence, skips a scan if another instance holds the lock, and commits the successful snapshot and status together. It persists a failed result and the UI identifies failed or stale measurements. The API and display do not include local/NAS storage and warnings are visible on the configuration panel; the user explicitly deferred extending these. Network enforcement and emergency-account administration remain unimplemented.

Focused evidence for the additional work: `StorageUsageSnapshotServiceTest` covers a completed measurement and failure before persistence; `StorageUsageControllerTest` covers denied and authorized access and overflow-safe threshold calculation; `StorageUsagePolicyServiceTest` rejects invalid budgets and percentages before any database or audit operation. These tests passed, as did the frontend TypeScript check. Tests do not establish scheduler concurrency across instances, transaction/audit behavior against the database, runtime UI appearance, or actual MinIO integration.

Follow-up: `StorageUsageSnapshotServiceTest` additionally verifies that a mocked advisory-lock refusal prevents a second scan and that the lock is released after success or a scan failure. This is not a PostgreSQL concurrency integration test. The local database reports Flyway version 690; V691 has not been applied.

Further work: V692 adds a disabled-by-default administrative network policy. `AdministrativeNetworkPolicyService` validates CIDR values, an active emergency account with configuration-management permission and that the current administrator would not be blocked; it writes before/after audit in the same transaction. The service has no controller or request interceptor and the policy is not enforced. The initial handler catalog is explicitly incomplete and not wired to enforcement. User lookups and the session-security read endpoint were identified as shared operations and excluded. A future implementation must complete the handler inventory and prevent later account/permission changes from invalidating the emergency recovery path before enabling enforcement.

Both V691 and V692 SQL scripts were applied successfully to disposable PostgreSQL 17 containers. A PostgreSQL advisory lock refused a second independent session during a held lock. The containers were stopped; the running application database was not modified. The focused network-policy service and catalog tests passed, including inactive emergency-account and current-admin lockout rejections. These are not end-to-end tests, nor do they validate audit persistence, concurrency of policy changes, real MinIO, or actual enforcement.

## Emergency-account protection and endpoint inventory follow-up

Source-confirmed: the designated emergency user depends on an active `app_users` account plus effective `settings.configuration.manage` permission via active Access Profiles and active Permission Sets. Changes to the user, profile membership/status, permission-set membership/status, or the set's permission items can therefore invalidate recovery. A guard must run in the same transaction as these changes, serialize against network-policy updates and re-evaluate the final effective permission using uncached data; rejecting only direct user suspension or removal from one profile is insufficient when permissions may be granted through multiple profiles. The change must not assign or preserve permissions implicitly.

GitNexus reports `UserManagementService` CRITICAL (8 direct dependencies, 63 processes) and `AccessProfileService` CRITICAL (4 direct dependencies, 58 processes). The catalog was expanded for reviewed settings, security policies, permission sets, document policies, report configuration and template administration. The catalog remains an incomplete, unwired inventory; tests verify that entries name existing controller methods and shared user/session lookup endpoints are excluded. It must not be used as a claim that all administration routes are protected. Focused catalog and network policy tests pass.

User approved changes to the critical user-management and authorization flows. GitNexus also rates `PermissionSetService` CRITICAL (4 direct dependencies, 58 processes). V693 is an unapplied proposed database guard: it serializes authorization/policy writes and uses deferred validation of the final transaction state so an enabled policy retains an active emergency user with effective configuration-management permission. A disposable PostgreSQL 17 fixture verified rejection of suspension, permission removal and profile deactivation; moving the grant within one transaction succeeded. Two concurrent transactions removing different redundant profile grants resulted in one commit and one rejection. The disposable database was removed.

**Unresolved before release:** `UserManagementService.suspendUser` calls `NotificationDispatcher` inside the transaction and the dispatcher may send email before commit. A deferred database rejection can therefore leave a misleading external notification even though the account change rolls back. The guard must not be considered release-ready until this path and equivalent side effects are guarded before delivery or made reliably after-commit, with negative integration tests. The migration has not been applied to the application database. The handler inventory and runtime network enforcement remain incomplete.

## 2026-10-28 follow-up (completion pass)

**Network.** The request filter (`AdministrativeNetworkConfig`) is wired and now has unit tests (inside the allowlist, outside it with an audited refusal, emergency account with an audited bypass, policy off, ordinary handler, recovery switch). Added: a server-side recovery switch `app.admin-network.recovery-disable` (environment `APP_ADMIN_NETWORK_RECOVERY_DISABLE=true`, then restart) that makes the filter ignore the policy, with a startup warning; `POST /settings/network-access/check-address`, which saves nothing and reports the address the server resolves for the caller under the typed proxies and whether the typed networks contain it (shown in the panel as "Check My Address"). The operation catalog listed a method that does not exist (`DocumentNameFormatController.deleteFormat`) and omitted the component endpoints; corrected, and a test now also checks that every protected controller name exists. The unresolved item of 2026-10-27 is addressed for the user-management flows: `suspendUser`, `terminateUser` and the participant-unavailable notice are sent after the transaction commits, in a transaction of their own (`NotificationDispatcher.dispatchIndependently`), so a rollback by the V693 deferred guard no longer leaves a message about a change that did not happen. Not done: the other flows that the guard protects (access profiles, permission sets) were checked for notifications and none was found, but this was a source search only; no negative integration test against PostgreSQL; V692/V693 are still not applied to the application database; the handler inventory is still incomplete and must not be read as full coverage of administration routes; the remote address behind the proxy depends on the trusted-proxy list being right (check with "Check My Address").

**Storage.** V694 adds `storage_usage_scan_state.warning_notified`. `StorageUsageAlertService` tells the active administrators with `settings.configuration.manage`, in the application only, once each time a successful measurement reaches the warning threshold, and arms again when the usage is back under it or no budget is set. The panel takes the budget in GiB, shows the share of the budget, the growth between the oldest and newest measurement (only when at least a day apart) and the days left at that rate, and shares by storage domain and file type. Unit tests cover the alert service, the panel and the growth calculation. Not verified: V694 against PostgreSQL, a real MinIO scan, the notification reaching a real user, the panel in a browser.

**Dashboard.** Role defaults gained keyboard/touch move buttons (the same move as dragging). Personal layout (drag, show/hide, width, reset to the role default) and role defaults by access profile with priority were already connected; no drag behaviour was verified in a browser. Widget visibility never grants data permission.

**Evidence.** Frontend: `tsc` clean; vitest for settings configuration and dashboard folders passed. Backend: the focused tests above passed. `detect_changes` was not run; no deployment, migration on the application database or browser check was done. This record does not assert GMP compliance.
