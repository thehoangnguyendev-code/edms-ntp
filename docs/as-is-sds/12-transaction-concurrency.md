# 12 — Transaction & Concurrency Behavior (AS-IS)

## Document
- `@Transactional` per mutating method (`cancelDocument`, `obsoleteDocument`, etc.); concurrency control = `@Version lockVersion` optimistic lock on `DocumentRecord` only.
- `obsoleteDocument`: status precondition (`fromStatus=="ACTIVE"`) is checked once early; several repository reads/writes (revision cascade, controlled-copy cascade) execute afterward within the same transaction before final save. This is a TOCTOU window bounded only by `@Version` on the Document row itself — it does **not** protect against a concurrent action on a Revision or Controlled Copy row that read a now-stale Document status earlier. Classify as `IMPLEMENTATION-GAP` candidate pending confirmation of whether Revision/Controlled-Copy-side guards independently close this window (they largely do — see below).

## Document Revision
- Sequence-aware pending-participant re-check (`RevisionService.requirePendingParticipant`) is performed **at the moment of** `completeReview`/`rejectReview`/`completeApproval`/`rejectApproval`, independent of and in addition to `@Version` — closes most of the "two reviewers act simultaneously" race by re-deriving "next pending in sequence" from a fresh read inside the transaction.
- `publishRevisionRecord`/`updateRevisionStatus`: no additional re-fetch beyond `@Version`; relies on optimistic locking to fail a concurrent double-publish attempt with an `OptimisticLockingFailureException` (standard JPA behavior, not custom retry logic observed in this pass for the Revision publish path itself).

## Controlled Copy — the most concurrency-hardened module traced so far
- **Async batch actions (distribute/cancel/recall) never operate on in-memory snapshots.** Event listeners (`onBatchDistributed`/`onBatchCancelled`/`onBatchRecalled`) receive only IDs and re-fetch every entity fresh from the repository inside their own `@Transactional` methods.
- **Explicit terminal-state guard before mutation** in `finalizeDistributedCopy` (`isTerminalControlledCopyStatus` check → `SKIPPED_TERMINAL` if a concurrent action already won) and `finalizeCancelledCopy` (explicit re-check for `STATUS_DISTRIBUTED`, returns `false` rather than throwing if the state changed). **`finalizeRecalledCopy` has NO equivalent guard** — asymmetry/gap (see `10-hidden-implementation-rules.md` #12).
- **On `OptimisticLockingFailureException`**, `finalizeWithRetry` (distribution async service) explicitly opens a **brand-new transaction** (`controlledCopyService.isControlledCopyInTerminalState(copyId)`, `@Transactional(readOnly=true)`) to determine who won the race, rather than trusting any cached state — code comment: "the only reliable way to learn who won the race is to re-read the copy's status in a brand-new transaction here." This is a deliberately engineered pattern, not incidental.
- **Print/download quota consumption uses atomic conditional bulk UPDATEs** (`controlledCopyRepository.consumePrint(id, printOnce)`, `consumeDownload(id, timestamp, downloadOnce)`) rather than read-modify-write Java mutation — avoids race conditions on print/download-once policies without needing optimistic-lock retry logic at all.
- **Startup recovery**: `resumePendingJobs()` (`@Scheduled(fixedDelay=30000)` in each async service) uses an atomic `claimPendingJob(jobId)` to prevent double-processing of the same job across multiple backend instances.
- **Scheduled jobs use distributed Redis leases**, not just `@Scheduled` alone: `ControlledCopyExpiryScheduler` (`"controlled-copy-expiry"`, 30 min) and `ControlledCopyBatchDiscrepancyScanner` (`"controlled-copy-batch-discrepancy"`, 15 min) both skip their run if the lease isn't acquired — safe for horizontally-scaled deployments.
- **Discrepancy scanner is intentionally read-only** (never self-heals a mismatch) — see `08-state-machines.md` §8.4.3.

## Cross-cutting concurrency question from the task brief: "frontend holds stale state" / "API request arrives after parent state changed"
- Backend-side, the Controlled Copy module is the best-evidenced: async finalize methods re-fetch and (mostly) re-check terminal state before mutating, so a frontend-initiated action arriving after the parent has already changed state is generally **rejected or no-op'd server-side** rather than corrupting data — except the confirmed `finalizeRecalledCopy` gap.
- For Document/Revision, the guard is a mix of hardcoded status preconditions (checked once per request, inside the transaction) plus `@Version` optimistic locking; no evidence yet of an additional "re-fetch and compare" pattern comparable to Controlled Copy's `isControlledCopyInTerminalState`. **UNKNOWN**: whether the frontend itself performs any stale-state detection (e.g., comparing a locally cached status before enabling an action button) — this is a frontend-code question not yet traced; see `21-known-unknowns-conflicts.md`.
