## Confirmed system-acknowledged limitations (not defects — do not "fix")
- `ControlledCopyBatchDiscrepancyScanner` is explicitly designed to be read-only/non-self-healing.
- `AccessEffectiveService` explicitly cannot resolve instance-specific actor scopes (AUTHOR/PARTICIPANT) in the abstract for a whole Access Profile, and says so in its own output.
- `SignatureTokenConsumptionService`'s `requireValidWithoutConsuming` gap (token can still expire/be replayed during a long async queue wait) is a self-documented, "tracked separately" residual gap in the code's own comments, not an independently discovered defect.

## Candidate IMPLEMENTATION-GAP items requiring a Decision Log entry (per CLAUDE.md) before treating as defects
1. `DocumentService.obsoleteDocument()`'s Controlled-Copy cascade and `RevisionService.obsoleteDistributedControlledCopies()` are two independent implementations of "obsolete this revision's distributed controlled copies" rather than one shared call — confirm whether this is intentional layering or accidental duplication. See `11-cross-workflow-dependencies.md` for the full divergence-risk analysis.
2. `RevisionWorkflowAction.OBSOLETE` and the `OBSOLETED` branch of `RevisionService.updateRevisionStatus` are fully specified but have zero callers — confirm whether a direct "obsolete this revision" user action is planned/removed/never-built.
3. `RevisionSnapshotAsyncService`/`RevisionSnapshotEvent` are dead code with real (but unused) stale-request-protection logic in their comments — confirm whether this was superseded intentionally by the synchronous `regeneratePublishingSnapshotIfConfigured` path, and whether the synchronous path's silent exception-swallowing (`log.warn` only) is acceptable for a GMP-relevant PDF rendition step.
4. `uploadRevisionFile` bypasses the hybrid authorization engine in favor of legacy permission helpers, despite a defined `UPLOAD_SOURCE` workflow action existing — confirm cutover status.
5. `finalizeRecalledCopy` lacks the terminal-state guard present in `finalizeDistributedCopy`/`finalizeCancelledCopy` — confirm whether recall's weaker concurrency safety net is acceptable given recall only ever moves Distributed→Obsoleted (a narrower race window than distribute/cancel). **Confirmed unmitigated by the frontend too** (`20-ui-api-service-mapping.md` item 6).
6. Storage "providers" for AWS S3/Azure/GCP/Google Drive/OneDrive/generic-SharePoint/Dropbox are simulated only, writing to local disk instead — confirm whether this is intentional placeholder/roadmap scaffolding or a misleading configuration surface that should be hidden/labeled until real integrations exist (`17-file-storage.md`).
7. Three independent dead "async event" mechanisms (`RevisionSnapshotEvent`, `AsyncEmailRequestedEvent`, `MfaOtpEmailRequestedEvent`) — confirm whether these are remnants of an abandoned architecture migration (in which case they may be safe to remove) or partially-built features awaiting a publisher (`13-async-scheduler-events.md`).
8. Five-plus QF-referenced notification types with no confirmed live trigger (Author/Co-Author assignment, Periodic Review due, Document Valid-Until reminders, Controlled Copy Request, four catalog-only events) — confirm which are deliberately out of scope for this release vs. genuinely missing (`14-notifications.md`).
9. E-signature is password-only + MFA hardcoded disabled — confirm this satisfies the organization's 21 CFR 11.200(a) interpretation, since code cannot make this regulatory judgment call (`16-electronic-signature.md`).
10. `MFA_DISABLED = true` hardcoded in `AuthService` — confirm whether this is a deliberate current-environment setting (e.g., pre-production) or an oversight, given MFA is otherwise a fully-built feature (`16`).
11. **Confirmed via targeted verification**: `DetailDocumentView.tsx` and `NewDocumentView.tsx` gate the "Obsolete Document" action differently — one defers purely to the server capability, the other combines it with a client-side re-derivation of the same three lifecycle preconditions. Confirm whether this divergence is intentional (e.g., `NewDocumentView`'s edit-mode context needs an earlier/optimistic check) or an unintended inconsistency that should be unified. See `07-workflows.md` WF-DOC-05 and the RESOLVED table above.

## QF vs. AS-IS architecture-level deviation (not a defect, but must not be assumed away)
The system replaces QF's fixed 7-role authorization matrix with a DB-backed permission-code + policy-engine model (`06-role-authorization-model.md` §6.0). Any SDS section that references "the Author role can X" must be understood as shorthand for "a user whose Access Profile grants the relevant permission code(s) and who satisfies the record-level actor scope," not a literal role check.
