# 16 — Electronic Signature (AS-IS)

Evidence: direct read of `service/AuthService.java`, `service/ElectronicSignatureService.java`, `service/SignatureTokenConsumptionService.java`, `auth/TokenService.java`, `controller/SharedSignatureController.java`.

## Capture mechanism: password re-entry only — no separate PIN/MFA
`AuthService.verifySignature(VerifySignatureRequest)` re-checks the **current session's own password** (`passwordEncoder.matches(request.password(), currentUser.getPasswordHash())`) — no separate PIN, no MFA challenge. `ElectronicSignatureService` hardcodes `AUTHENTICATION_METHOD = "PASSWORD"` with an explicit code comment: *"Electronic signatures are intentionally password-only (never configurable) — login MFA/SSO remains an account security feature, but is not an alternative signing mechanism."* On success, `TokenService.createSignatureToken(currentUser)` mints a short-TTL (`app.auth.signature-token-ttl-minutes`) JWT of type `"signature"` with a fresh random `sid` nonce claim. Both the verify success/failure and the resulting `VERIFY_E_SIGNATURE` action are logged separately (`AuditService.log("esign_verify_success"/"esign_verify_failed", ...)` and `AuditTrailService.logAs(...,"VERIFY_E_SIGNATURE",...)`).

## 21 CFR 11.200(a) mapping — flag for Decision Log, not a code defect
Identity (component 1) is established by the already-authenticated session; password (component 2) is re-verified at sign time — matches the "continuous session, subsequent signings need only one additional component once identity was established at first signing" reading of 11.200(a)(1)(ii), provided the original login required at least identification-code+password (it does) or MFA. **`MFA_DISABLED = true` is hardcoded in `AuthService`** (not environment-configurable per the code comment) — so in this deployment, "two distinct components used together" currently reduces to username/password at login + password-only at signing: effectively the same single factor (password) reused across both steps. Whether this satisfies 11.200(a)(1) strictly depends on whether login-time identification-code+password count as the two components (a defensible reading) — **UNKNOWN/interpretation-dependent, not a code defect**. Per CLAUDE.md's guardrails, this should be a **named Decision Log entry**, not something code alone can resolve.

**No re-authentication-after-session-break requirement was found**: `verifySignature` does not check how long the current session/JWT has been idle before allowing a password-only re-verification — it only requires *a* correct password at the moment of signing. `IMPLEMENTATION-GAP/UNKNOWN`: no distinct "if idle beyond X minutes, require full re-login" gate feeds into the signature flow, separate from the general session/access-token TTL. This is relevant to 11.200(a)(1)(i) ("both components entered ... following any break of system action").

## Signature meaning, printed name, date/time — persisted per 21 CFR 11.50/11.70
Entity: **`ElectronicSignature`**, one row per signing action. Captured (`createRevisionSignature`/`createEntitySignature`): `entityType`/`entityId` (+ `document`/`revision` FKs for revision signatures), `user` FK plus **snapshotted** `username`/`fullName`/`position`/`email`/`department` (printed name/title captured at signing time, not live-joined — same deliberate snapshot pattern as `AuditLog`'s actor fields), `meaning` (normalized uppercase code — confirmed full vocabulary: `PREPARED`, `SUBMITTED_FOR_REVIEW`, `REVIEWED`, `APPROVED`, `TRAINING_CONFIRMED`, `PUBLISHED`, `OBSOLETED`, `CANCELLED`, `CONTROLLED_COPY_REQUESTED`, `CONTROLLED_COPY_DISTRIBUTED`, `CONTROLLED_COPY_RECALLED`, `CONTROLLED_COPY_DISTRIBUTION_CANCELLED`, `CONTROLLED_COPY_DESTROYED`, `CONTROLLED_COPY_REISSUED`, `AUDIT_RECORD_EXPORTED`), `reason`, `comment`, `signedAt` (Instant), `timezone` + `timestampDisplay` (rendered per admin-configured format), `authenticationMethod` (always `"PASSWORD"`), `signatureId` (human-readable sequence `ESIG-yyyy-NNNNNN`), `verificationId` (`"VERIFY-" + UUID`), `ipAddress`/`userAgent`. Revision signatures additionally capture `documentChecksumBeforeSign`/`documentChecksumAfterSign`/`sourceFileVersionId` — **binds the signature to the exact file content signed**, a strong `QF-MATCH`-and-beyond control for 11.70's "prohibit modification... movement" intent applied to the underlying document, not just the signature row. Every signature creation pairs with an `AuditTrailService.logAs(..., "DOCUMENT_ELECTRONICALLY_SIGNED"/"ENTITY_ELECTRONICALLY_SIGNED", ..., saved.getId())` call, linking the audit row to the signature row via `signatureId`.

## Immutability / linkage to the record (11.70)
No update method on `ElectronicSignature` was observed being called anywhere outside creation — `save(signature)` only appears at initial creation in both `createRevisionSignature` and `createEntitySignature`; reads elsewhere are all `@Transactional(readOnly=true)`. As with `AuditLog` (`15-audit-trail.md`), this is **convention-based immutability** (no delete/update call sites found), not a database-enforced constraint discovered in this pass. The signature is durably tied to its Document/Revision/entity via FK and to the audit trail via `signatureId` — satisfying "linked to the record" via foreign-key association. A genuine 11.70 "prohibit modification, duplication, or movement" guarantee would additionally require confirming no admin/support code path reassigns a signature's `entityId`/`revision` post-creation — **none was found**, but a database-level trigger/constraint check was out of scope for this pass.

## Signature token: single-use, replay-protected
`SignatureTokenConsumptionService.requireAndConsume(rawToken, currentUser)` is the single choke point — explicitly documented as **replacing four previously-duplicated, non-tracking implementations** in `DocumentService`/`RevisionService`/`ControlledCopyService`/`ElectronicSignatureService` (`IMPLEMENTATION-DISCOVERED`: evidence of a prior refactor that consolidated scattered signature-validation logic):
1. Parses the JWT, confirms `parsed.principal().userId().equals(currentUser.getId())`.
2. Attempts `usedSignatureTokenRepository.save(new UsedSignatureToken(tokenId, currentUser, now))` — `tokenId` (the JWT's `sid` nonce claim) is the PK of `UsedSignatureToken`. **A replay of the same token in a different transaction hits the DB PK/unique constraint**, throws `DataIntegrityViolationException` → translated to `UnauthorizedException("This electronic signature has already been used and cannot be reused")`.
3. Within the **same transaction**, a second internal call with the same token is treated as idempotent via `TransactionSynchronizationManager` resource binding (`"signature-token-consumed:" + tokenId`) — necessary because several action methods validate the token once at the top and then pass the same raw token into `ElectronicSignatureService.createEntitySignature(...)`, which validates it again as part of the *same* action (not a replay attempt).

Also present: `requireValidWithoutConsuming(...)` — validates ownership and non-consumption **without** consuming, used by the Publishing Workspace's async accept-then-sign-later flow to fail fast on an already-invalid/expired/replayed token at accept time rather than only discovering it minutes later on the worker thread. **Acknowledged, documented residual gap** (the code's own comment, not an independent finding): this does not solve a token expiring during a long queue wait or a backend restart before the async worker actually consumes it — described in-code as a "larger contract change tracked separately." Flag in `21-known-unknowns-conflicts.md` as a known, self-acknowledged gap, not a newly discovered one.

## Cross-reference to lifecycle e-signature meanings (already confirmed, see `08-state-machines.md`)
Document Cancel: no signature; Document Obsolete: `OBSOLETED`. Revision: `completeEditing`→`PREPARED`, `submitForReview`→`SUBMITTED_FOR_REVIEW`, `completeReview`→`REVIEWED`, `completeApproval`→`APPROVED`, `rejectReview`/`rejectApproval`→`REJECTED`, `completeTraining`→`TRAINING_CONFIRMED`, `publish`→`PUBLISHED`, `cancel`→`CANCELLED`. Controlled Copy: request→`CONTROLLED_COPY_REQUESTED` (once per batch), distribute→`CONTROLLED_COPY_DISTRIBUTED`, recall→`CONTROLLED_COPY_RECALLED`, cancel→`CONTROLLED_COPY_DISTRIBUTION_CANCELLED`, destroy→`CONTROLLED_COPY_DESTROYED`, replace→`CONTROLLED_COPY_REISSUED`. Audit export→`AUDIT_RECORD_EXPORTED` (`15-audit-trail.md`).
