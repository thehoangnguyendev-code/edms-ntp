# 14 — Notifications (AS-IS)

Evidence: direct read of `service/NotificationDispatcher.java`, `service/EmailNotificationService.java`, `service/RevisionService.java` (notification dispatch points), `service/ControlledCopyService.java`, `bootstrap/NotificationEventCatalogBootstrap.java`, `service/ControlledCopyExpiryScheduler.java`, `service/AuthService.java`.

## Two real dispatch paths
1. **Policy-driven path — `NotificationDispatcher.dispatch(eventCode, recipients, variables)`**: the only place that resolves a `NotificationPolicy`, renders both IN_APP and EMAIL active template versions, and decides IMMEDIATE vs. digest/quiet-hours deferral. Mandatory (GMP) events always fire immediately on every enabled channel, bypassing recipient preference/quiet-hours/digest settings; optional events respect them. Non-immediate email is written to `NotificationDispatchQueue`, flushed later by the hourly `NotificationDigestScheduler`. **Sending here is synchronous within the caller's transaction commit boundary** — no async-event indirection; deferral is a DB row, not an event.
2. **Legacy template path — `EmailNotificationService.sendDocumentWorkflowNotification`/`sendControlledCopyNotification` → `sendToRecipients`**: looks up an active `EmailTemplate` by type, sends directly via `EmailService`, and additionally calls `dispatchPolicyNotification(recipient, variables)` internally if the caller supplied a `notificationEventCode` variable. `isPolicyManaged(variables)` suppresses the duplicate in-app inbox row, but **the email itself may be sent by both the legacy template lookup and the policy engine's own email version for policy-managed events using this path** — flagged as a **latent duplicate-email risk, UNKNOWN, not confirmed either way** without deeper tracing.

## MFA OTP email
Sent synchronously via `AuthService` calling `emailService.sendEmail(...)` inside `runAfterCommit(...)` — **not** via the dead `MfaOtpEmailRequestedEvent` (see `13-async-scheduler-events.md`). `MFA_DISABLED = true` is hardcoded in `AuthService`, so MFA challenge/OTP is currently bypassed system-wide; the OTP send code path itself is intact and reachable if that flag were flipped.

## Summary of confirmed IMPLEMENTATION-GAPs
Five QF-referenced notification types have **no confirmed live trigger**: Author/Co-Author assignment, Periodic Review due, Document Valid-Until 7-day/1-day expiry, Controlled Copy Request, plus four catalog-defined-but-never-fired event codes (`audit_trail.review_campaign_assigned`, `audit_trail.export_completed`, `system.preference_updated`, `system.maintenance_scheduled`). These should be raised as Decision Log items per CLAUDE.md guidance — do not assume they're bugs; some may be deliberately deferred/roadmap items.
